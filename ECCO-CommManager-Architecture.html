4 Recommendations — Resiliency, Performance & Scalability

Resiliency

Resiliency

R1 — Polly Resilience Pipelines on All HTTP Calls

VentureFusion and Documentum ECM calls use manual 401-retry logic today with no circuit breaker or exponential back-off on transient failures.

  • Replace ad-hoc retry with Microsoft.Extensions.Http.Resilience (built on Polly v8)
  • Add per-client circuit breakers: open after 5 consecutive failures, half-open after 30s
  • Exponential jitter back-off: 1s → 2s → 4s (+jitter) × 3 attempts
  • Expose circuit state via health check endpoint already in place
Resiliency

R2 — Outbox Pattern for DB + Service Bus Atomicity

Current flow writes to SQL then publishes to Service Bus separately. A crash between these two steps causes a lost message or duplicate.

  • Implement transactional outbox: write the message to an OutboxMessages SQL table in the same EF Core transaction as the domain write
  • A background worker (or Azure Function) reads the outbox table and publishes to Service Bus, then marks sent
  • Guarantees at-least-once delivery without distributed transactions
Resiliency

R3 — Dead-Letter Queue Alerting & Replay

NServiceBus has error/retry queues configured, but there is no alert when messages land in the dead-letter queue, and no replay UI.

  • Add Azure Monitor alert on Service Bus Dead-Letter message count > 0
  • Build a minimal admin endpoint (or use ServicePulse) to replay failed messages
  • Persist dead-letter context to NonRecoverableErrorLog table (already modeled)
  • Set up PagerDuty / Teams notification for on-call escalation
Resiliency

R4 — Geo-Redundant SQL + Failover Group

Database is a single-region Azure SQL instance in East US 2. A regional outage stops all correspondence processing.

  • Enable Active Geo-Replication to West US 2 (paired region)
  • Configure an Auto-Failover Group with automatic failover policy
  • Update connection string to use the failover group DNS endpoint (transparent to EF Core)
  • Test failover quarterly via chaos engineering drill
Resiliency

R5 — Key Vault Regional Redundancy & Secret Rotation

Secrets cached for 4 hours; if Key Vault is unreachable at cache expiry the service degrades. PGP keys and VF credentials have no automated rotation.

  • Enable Key Vault soft-delete and purge protection (if not already set)
  • Add a fallback Key Vault in the paired region; resolve via DNS failover
  • Implement secret rotation: Azure Automation runbook triggers rotation on a schedule; new version cached on next request
  • Raise an alert if GetSecretAsync latency exceeds 500ms

Performance

Performance

P1 — DocID Pool Pre-warming & Batch Size Tuning

DocID generation is a synchronous SOAP call that holds a semaphore during the request path. Under load this becomes a serialization bottleneck.

  • Move DocID replenishment entirely to a background IHostedService; remove it from the request path
  • Pre-warm on startup: fill pool to 2× threshold before accepting traffic
  • Tune DocIdCount (batch size) to cover peak-hour throughput with 5-min buffer
  • Expose pool depth as an Application Insights custom metric for autoscale decisions
Performance

P2 — IHttpClientFactory + Named Clients for VF & ECM

VentureFusionService and DocumentIdGeneratorService both instantiate raw HttpClient objects as fields, which causes socket exhaustion under load and doesn't pool connections.

  • Register named/typed clients via services.AddHttpClient<IVentureFusionService, VentureFusionService>()
  • Configure SocketsHttpHandler with PooledConnectionLifetime = 2min
  • Combine with Polly resilience pipelines (R1) on the same registration
  • Remove all new HttpClient() field initializers
Performance

P3 — Azure Redis Cache for Distributed Secrets & Token Cache

In-memory SecretsCacheService is per-instance; in a multi-instance App Service plan each instance fetches secrets independently from Key Vault, multiplying KV request load.

  • Replace IMemoryCache with IDistributedCache backed by Azure Cache for Redis
  • Single Redis instance serves all App Service instances; KV calls drop proportionally
  • Use Redis for VF and DocID bearer tokens as well
  • Keep in-memory L1 as a 60s read-through for hot-path performance
Performance

P4 — Async EF Core Queries + Compiled Queries

All EF Core calls are async (good), but high-frequency status queries (by DocId, ClaimNumber) re-compile expression trees on every call.

  • Add compiled queries (EF.CompileAsyncQuery) for the three highest-volume lookups
  • Add a non-clustered index on CorrespondenceRequest.PolicyNumberHash and ClaimNumber
  • Enable query result caching in Redis for read-heavy status endpoints (5-second TTL)
  • Enable EnableRetryOnFailure in SQL connection resilience options
Performance

P5 — APIM Response Caching for Status Endpoints

Read-only status endpoints (GET /status/docid, /status/claim) are called frequently and return data that is stable for several seconds.

  • Add APIM <cache-lookup> / <cache-store> policies with 10s TTL on GET status endpoints
  • Vary cache key by Authorization header to preserve per-caller isolation
  • Reduces App Service CPU and SQL reads by an estimated 30–50% at peak

Scalability

Scalability

S1 — App Service Autoscale Based on Service Bus Queue Depth

App Service scales on CPU/memory by default, but the real pressure signal is Service Bus queue depth — message backlog, not instance CPU.

  • Configure Azure Monitor autoscale rule: scale out when ActiveMessageCount > 200, scale in when < 20
  • Set min=2 instances for availability, max=10 for cost control
  • Pair with NServiceBus concurrency setting (LimitMessageProcessingConcurrencyTo) per instance
Scalability

S2 — Partition Service Bus Topics by Delivery Method

Mail and ePresent deliveries have very different latency profiles. A slow mail batch delays ePresent (email) confirmations.

  • Create separate queues/subscriptions: process-mail and process-epresent
  • Route in CommManagerController based on request.Process.DeliveryMethod
  • Scale ePresent consumers independently (lower latency SLA)
  • Enables per-channel throttling and priority processing
Scalability

S3 — Migrate Azure Functions to Flex Consumption Plan

Azure Functions on a Consumption plan cold-start delays hurt the reconciliation latency; on Dedicated plan they over-provision.

  • Move to Flex Consumption plan (GA 2024): always-warm instances + per-execution scale
  • Enables VNet integration needed for private endpoints (Data Subnet)
  • Reduce reconciliation latency from minutes to seconds
Scalability

S4 — Event-Driven Archive Status via Service Bus (Replace Timer Poll)

DocumentStatusSync and ArchiveReconciliation timer-poll ECM on a fixed schedule, creating unnecessary load and delayed status updates.

  • Request ECM to emit a webhook / event on archive completion
  • Publish to Service Bus topic; DocumentStatusSync becomes an event-driven Function
  • Status latency drops from minutes (poll interval) to seconds
  • Reduces ECM SOAP call volume by ~90%
Scalability

S5 — CQRS Read Model for Correspondence Status Queries

All write (process request) and read (status queries) operations share the same SQL database and EF Core model, competing for connections at scale.

  • Introduce a read-optimized projection table (updated by event handlers)
  • Route GET /status/* to a read replica (Active Geo-Replication secondary)
  • Eliminates read/write contention on primary SQL; improves write throughput
  • Opens path to materialized views and Redis-backed read models

5 Top 5 Agentic AI Implementation Ideas

Idea 01

Intelligent Correspondence Routing Agent

Replace the static RoutingConfiguration lookup table with an AI agent that dynamically selects the optimal delivery method and handler pipeline based on customer profile, document type, history, and real-time channel health.

  • Analyzes past delivery outcomes per customer segment
  • Switches from Mail to ePresent automatically if mail failure rate is high
  • Learns from delivery confirmations fed back via DocumentStatusSync
  • Falls back to static routing if confidence score < threshold
Impact: ↑ First-attempt delivery rate | ↓ Failed correspondence
Idea 02

Autonomous Failure Remediation Agent

An LLM-powered agent that monitors the Service Bus dead-letter queue and NServiceBus error queues, diagnoses root cause, and autonomously retries, reroutes, or escalates failed messages — with human approval for high-risk actions.

  • Classifies failures: transient / data / external-service / config
  • Auto-fixes known patterns (bad address → verify → retry)
  • Drafts a remediation plan and requests approval for novel failures
  • Integrates with Teams / PagerDuty for human-in-the-loop escalation
Impact: ↓ Mean Time to Recover | ↓ On-call burden
Idea 03

Natural Language Correspondence Query Agent

An agent exposing a chat-style interface that lets operations staff query correspondence status using plain English instead of constructing API calls. Backed by Claude with tool-use to call existing CommManager API endpoints.

  • "Show me all failed mail deliveries for claim 123456 this week"
  • "Retry all ePresent failures where email address was invalid"
  • "Generate a delivery success rate report by document type for Q2"
  • RBAC-gated: same OIDC roles as API; no new attack surface
Impact: ↑ Ops productivity | ↓ Support ticket volume
Idea 04

Predictive DocID Pool Management Agent

Replace the reactive threshold-based replenishment with an ML forecasting agent that predicts DocID consumption based on time-of-day, day-of-week, and upstream event patterns, pre-generating IDs before the pool depletes.

  • Trains on historical CorrespondenceRequest volume data
  • Issues replenishment SOAP calls 15–30 min before predicted depletion
  • Eliminates the in-request DocID generation path entirely
  • Reduces SOAP call spikes; improves Documentum ECM relationship
Impact: ↓ API latency p99 | ↓ DocID generation errors
Idea 05

AI-Powered VentureFusion Payload Validation & Enrichment Agent

An agent that intercepts the VentureFusion payload before RequestCompositionHandler, validates completeness against document-type-specific rules, auto-enriches missing optional fields from policy/claims data, and predicts whether VF will accept the submission.

  • LLM-generated validation rules derived from VF rejection history
  • Auto-corrects common data quality issues (name casing, ZIP formatting)
  • Confidence-scored: only applies enrichment when confidence > 95%
  • Logs enrichment decisions for audit trail compliance
Impact: ↑ VF first-pass acceptance rate | ↓ Rejection rework
